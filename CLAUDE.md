# billlinphotos.com — notes for Claude

Bill Lin's street-photography site. Plain static HTML/CSS/JS, no build step. Hosted from this repo (Cloudflare Pages auto-deploys `main`). The owner edits by asking Claude in chat; he does not edit code himself. Reply to him in Traditional Chinese (Taiwan).

## Structure
- One `.html` file per page. Every page has the same `<head>` and `<main>` wrapper; header, mobile menu and footer are injected by `js/main.js` (the copyright footer is placed inside the bottom of the last section of `<main>`, over its photo or colour, with no band of its own; the year is automatic) — edit nav links, Instagram/YouTube URLs and the footer there, not in each page.
- `css/style.css` — all styles; colors/fonts are tokens at the top (`--gray`, `--sage`, `--serif` = Cormorant Garamond, `--sans`). The owner wants one font: everything is Cormorant Garamond (body default, buttons inherit) except the top navigation links (`.site-nav a`) and the Gallery map's "Explore by city" label (`.map-eyebrow`), which use `--sans`. Small UI text is sized up a little because Cormorant reads small.
- `js/config.js` — the cart's shipping note; prices and SKUs live in `functions/_lib/catalog.js` (see Shop below).
- `functions/` — Cloudflare Pages Functions for checkout and fulfilment; `tests/shop.test.mjs` tests them.
- `images/` — all photos, flat folder, named by camera file number (e.g. `DSC05015.jpg`).
- `favicon.svg` + `apple-touch-icon.png` (BL monogram), `sitemap.xml`, `robots.txt`, `_headers` (Cloudflare cache headers: images 30 days; CSS/JS revalidate on every visit so edits show up at once).
- Every public page's `<head>` has a page-specific `description`, `canonical` (pretty URL without `.html`, as Cloudflare Pages serves it), Open Graph tags (`og:image` = the page's lead photo, absolute `https://billlinphotos.com/images/...`) and `twitter:card`; `cart.html` and `404.html` are `noindex`. A new page gets the same tags and a line in `sitemap.xml`.

## Common edits
- **Add photos to an album:** add `<figure class="zoom"><img src="images/NAME.jpg" alt="..."></figure>` inside the `.masonry` (no `loading="lazy"` in masonry) or grid. A `data-group` ancestor scopes the lightbox's prev/next.
- **New blog post:** copy `autumn-in-boston.html` (keep `data-page="blog"`). In `blog.html` the newest post is the `.post-card.featured` article (photo left, text right); move the previous featured post into `.post-grid` as a plain `<article class="post-card">` (same inner markup, image `sizes="(max-width: 760px) 92vw, 44vw"`), then put the new post in the featured slot. Each card has meta (date · city; no reading time), title, a 2–3 sentence excerpt taken from the post, and "Read the story →".
- **New city album:** copy `boston.html`. In `gallery.html`, turn that city's map pin from `<g class="pin soon" tabindex="0" ...>` into `<a class="pin live" href="CITY.html" aria-label="CITY photos">`: copy the Boston pin's structure (callout group with leader path, label box and label text; halo r=11; hit r=7; dot r=5.5), keep the city's own coordinates, and drop the "Coming soon" tip text (live label box is 24 tall, label baseline at leader end +5). Then turn its `<span>` in `.city-list` into `<a href="CITY.html">CITY</a>`. `.city-list` is the touch-screen-only button grid (none on desktop); it shows exactly 6 cities, ordered by album photo count (most first, ties in the current order) — currently Boston, New York, Taipei, Kaohsiung, Fukuoka, Tokyo; Sydney and Melbourne are map pins only. Label box widths are set by `js/main.js`. To add a brand-new city, project it with d3 geoNaturalEarth1 fitted to the 1000×470 viewBox from world-atlas countries-110m without Antarctica (examples: Boston 320,136 · Taipei 828,191 · Sydney 897,381); the callout goes from the dot to (x+14, y−14), then horizontally to x+32.
- **New product:** see Shop below.

## Photos
The owner wants the site as sharp as possible. He sends originals (often 30–50 MB, sometimes HEIC, often without filenames; photos pasted into chat arrive downscaled to ~2576 px, so ask for file attachments when a large version matters). Never commit originals (Cloudflare Pages rejects files over 25 MiB). Every photo gets two versions, all JPEG, EXIF orientation fixed, progressive:
- `images/sm/NAME.jpg` — long edge 1200 px, quality 85
- `images/NAME.jpg` — long edge up to 2560 px, quality 88, 4:4:4 chroma
The owner does not want visitors downloading his photos, so nothing larger than 2560 px is published (the old 4000 px `images/full/` tier was removed; print-resolution originals live only in the private R2 bucket). `js/main.js` + `css/style.css` block right-click on photos, dragging images, and iOS/Android long-press save; keep this when adding new image types.
Apply light unsharp mask (radius 0.6, 45%, threshold 2) only after a downscale below 75%.
Every `<img src="images/NAME.jpg">` carries `srcset="images/sm/NAME.jpg 1200w, images/NAME.jpg <width>w"`, a `sizes` value matching its layout (see existing tags) and `decoding="async"`; the lightbox shows the same 2560 px image and can be zoomed (mouse wheel, pinch, double-click/double-tap, − / + buttons, keyboard +/−) and dragged to pan; on product pages (a single `figure.zoom[data-group]`) the prev/next arrows are hidden. CSS backgrounds use `images/NAME.jpg`.

## Shop (PayPal checkout + automatic Prodigi fulfilment, Cloudflare Pages Functions)
The owner tried a headless Shopify setup (modelled on skypathstudio.com) but dropped it for now because the monthly fee doesn't pay off yet; the shop is back to PayPal + Prodigi with no monthly cost. He may move to Shopify later once prints sell regularly (the Shopify code is in git history, commit `4a61709`…`3119f6c`).
- Flow: cart in the browser (localStorage `billlin-cart`: `{slug, variant, quantity, title, price (cents, display only), image}`) → "Checkout" POSTs the lines to `/api/checkout` → one PayPal order priced from the server catalog → buyer pays on PayPal → `/api/paypal-return` captures and redirects to `order-success.html` (which empties the cart) → PayPal webhook `/api/paypal-webhook` verifies the event, reads the order from PayPal and creates one Prodigi order (marker in R2 `orders/<id>.json` so it's never printed twice). A declined payment returns to `cart.html?payment=failed`. Until the PayPal keys are set, checkout answers 503 and the cart says "Online ordering is coming soon."
- `functions/_lib/catalog.js` is the source of truth: products keyed by handle (= page filename = `.product-info[data-handle]`), each variant's price (cents) and Prodigi SKU, the print file (`r2:NAME.jpg` in the private `PRINT_FILES` R2 bucket, served to Prodigi by `/api/print-file/NAME?token=PRINT_FILE_TOKEN`), `SHIPPING` (flat per order; now free) and `PRODIGI_SHIPPING_METHOD`. The SKUs are placeholders to check in the Prodigi catalog; the postcard SKU is literally `CHECK-PRODIGI-POSTCARD-SKU`. Print files: the owner's full-resolution originals live on his Mac in `~/Desktop/Boston/Edited/` (camera-numbered JPEGs); copies renamed to the catalog file names are in `~/Desktop/Boston/print-files/` for him to upload to R2 (files are 30–50 MB, too big for the browser upload tool). Secrets (`PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `PAYPAL_WEBHOOK_ID`, `PAYPAL_ENV`, `PRODIGI_API_KEY`, `PRINT_FILE_TOKEN`, `SITE_URL`) are set by the owner in the Cloudflare Pages dashboard; README.md has the setup steps in Chinese. Never ask him to paste them into chat.
- Product page: the option buttons in `.product-options` (`<div class="options" aria-label="Material">` with `<button data-value="…" data-price="…">`, one group per product) ARE the options; `js/main.js` re-renders them with prices. `data-value`/`data-price` must match the catalog — `tests/shop.test.mjs` checks this (run: copy `functions` + the test into a scratch dir with `{"type":"module"}` package.json, then `SITE_ROOT=$PWD node SCRATCH/shop.test.mjs`). Black pill "Add to Cart" → "Added" → cart drawer.
- Cart drawer ("Your Cart", from the right over a blurred backdrop): item cards (thumbnail, title, variant, line price, − qty + stepper, trash; max 10), Subtotal, shipping strip (`js/config.js` `shippingNote`, keep in line with `SHIPPING`), black pill Checkout, "Secure checkout · PayPal and cards accepted". Header cart icon (round sage count badge) opens it; `cart.html` shows the same view as a page.
- There is no returns/refunds page (the owner had one made, then asked to delete it).
- New product: add it to `PRODUCTS` in the catalog, upload its print file to R2, copy `transient-serenity.html` (portrait) or `boston-public-library.html` (landscape) to `<handle>.html`, set `data-handle`, title, photo, description, room-view thumbnails and option buttons, add a `.product-card` to `shop.html` and a sitemap line, then run the test.
- Product page layout: `.product-info` holds `.product-text` (h1 + desc) and `.buy-box` (options, price, Add to Cart, notes). Landscape/panorama photos (width/height ≥ 1.25; `js/main.js` sets `.product-layout.wide`, also written in the HTML to avoid a flash) go full width on top with text and buy-box below in two columns (image `sizes="92vw"`); portrait/square photos sit left of the text and are capped at the window height so the whole print shows without scrolling.
- Product gallery: each product page has `.product-gallery` = `figure.zoom.pg-main` + `.pg-thumbs` (buttons with `data-src`/`data-srcset`): the print, then room views of the print on a wall (the owner wants at least three, photo-realistic — NOT illustrations; the drawn ones from `tools/mockups.js` were rejected and removed). Room views are made by `python3 tools/roomviews.py images/NAME.jpg HANDLE` from the owner's free-licence room photos in `tools/rooms/room0-3.jpg` (old artwork erased and wall refilled with real wall texture, the print framed per room — all black frames (owner's choice): thin black / black+mat / black+mat / thin black — warped to the wall's perspective, shadowed and matched to the room light) → `images/mockups/HANDLE-1..4.jpg` (long edge 2000) + `sm/` (1000); then add one `.pg-thumb` per view. Each print has two sets: framed views `HANDLE-1..4` (`data-material="Framed Print"`) and gallery-wrapped canvas views `HANDLE-canvas-1..4` from `roomviews.py … --canvas` (`data-material="Canvas Print"`; no frame, wrapped edge on the side the camera sees, deeper shadow). `data-material` must equal the option's `data-value`: only the chosen material's views are shown (plus the plain print, which has no data-material), and clicking a material jumps the main picture to its first room view; arrows, keys, swipe and the lightbox only step through the shown thumbs. New room photos can only come from the owner (this workspace cannot download from stock sites); add each to `ROOMS` in the script with its erase quads, wall-plane quad, hanging box and frame style. The main picture sits in a fixed-size stage (`--stage` = the print's aspect ratio, set by js/main.js) so switching views never resizes the page; every picture (print and room views, main and thumbnails) is shown whole with `object-fit: contain` — the owner does not want anything cropped. Portrait prints on computer: three columns — picture, then a vertical column of thumbnails right beside it spanning the picture's height, then the text/buying (`.product-gallery` is `display: contents` there; this is the layout the owner drew); phones and landscape prints: thumbnails in a row below. With only one thumb the strip is hidden. Thumbnails switch the main picture, ‹ › arrows on the main picture (`.pg-arrow`, added by js/main.js; shown on hover on computers, always on phones) step through the views, so do the keyboard ← → keys (ignored while the lightbox, cart or menu is open), swipe works on phones, and the lightbox browses all of them.

## Commits
After any change to `css/` or `js/`, run `python3 tools/stamp_assets.py` before committing: it puts a content hash on every `css/style.css`, `js/main.js` and `js/config.js` link (`?v=…`). The billlinphotos.com zone forces a 4-hour browser cache on CSS/JS, so without a new `?v=` visitors keep the old files. New pages must use the same links (copy them from an existing page, then re-run the script).
Commit straight to `main` with a short message describing the change; the site redeploys in about a minute.
